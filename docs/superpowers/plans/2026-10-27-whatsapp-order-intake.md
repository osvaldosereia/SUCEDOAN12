# WhatsApp Flow and Catalog Order Intake Plan

> Execution plan for the next Admin backend slice. Follow `superpowers:executing-plans` when resuming implementation.

**Goal:** Accept Flow submissions and native WhatsApp Catalog carts as independent order intents, request explicit confirmation, then create exactly one order in the canonical Admin/Bling pipeline.

**Current implementation slice:** Local Meta event extraction, private Flow session/intake and immutable catalog snapshots, AES/RSA Flow data exchange candidate, separate Flow/Catalog confirmation and conversion paths, dedicated order-confirmation claim/sender, authenticated Catalog preparation UI, a signed ingress bridge, an Admin queue for opaque-sender messages with an acknowledge-only review state, and a staff-authenticated action that sends a published basket Flow from `/atendimento`. All database changes remain unapplied migrations; the bridge is not deployed and the Meta callback is unchanged. The complete production path remains unverified.

**Canonical project:** Supabase `ssbesxgaijknwsjbsbcz` (“Dona Antônia”). No remote DDL, function deployment, Meta webhook change, message send, or Bling write is permitted in this implementation slice.

## Fixed product decisions

1. Flow and every Catalog cart are separate order intents. Never merge by conversation, sender, time window, matching products, or close timestamps.
2. A Flow submission and a Catalog cart each receive their own confirmation summary and action. If a Catalog cart arrives after Flow, it becomes a new intent even in the same conversation.
3. Flow completion and Catalog submission are not sufficient to reserve stock or enter production. The customer must explicitly confirm the server-priced summary.
4. The summary lists products and quantities plus one grand total; omit per-item prices as requested.
5. There is no commercial expiration. A pending intent remains reviewable indefinitely. Flow session/token TTLs remain security controls and are not order-merge windows.
6. On confirmation, recalculate prices, hidden basket extras, and stock from the canonical database. If material values changed since the quote, create a new quote and request a fresh confirmation.
7. Catalog webhook `item_price` and currency are untrusted evidence; the Admin price/catalog mapping and server calculation are authoritative.
8. Store provider sender ID as opaque text separately from nullable E.164. Never fabricate a phone or link a customer on name similarity. Only link automatically when the existing canonical resolver returns one unambiguous identity.
9. Keep the canonical order `source` compatible with existing triggers (initially `manual_whatsapp` if the audit remains valid); record `flow` or `catalog` in a structured, versioned `checkout_snapshot` field and project that as the Admin origin label.
10. Never call `create_vitrine_cart_order_v3` for a draft: it reserves at creation. Never call `create_canonical_cart_order_v2` as-is: it does not accept the inbound event key and creates through the storefront path before changing source.
11. Supabase is the operational source for basket definitions, mold positions/options, shared-item option library, product availability, photos and pricing. Shared-item options are propagated into matching `basket_mold_position_options`; Flow must use that final per-position list and must not create duplicate screens from the library. The old runtime's GitHub `baskets.json` is historical evidence only; the greenfield runtime consumes immutable snapshots built from canonical Supabase configuration so Admin edits and customer Flow screens cannot diverge.
12. Do not publish a Supabase mold while any enabled position has zero eligible active WhatsApp products. The current audit has 21 such positions across the audited active molds; resolve them or explicitly deactivate the affected positions/baskets before publishing. The five empty shared registry records are not separate Flow slots; any affected final position remains blocked by the same position-level gate.
13. Do not reuse legacy `public.whatsapp_flow_sessions.catalog_commit/catalog_revision` for the greenfield snapshot. Keep the old Git-backed runtime contract intact and create a versioned private session record that refers to the immutable Supabase snapshot hash; its 24-hour technical token TTL is independent of a non-expiring commercial intent.
14. An account may have multiple enabled, published order Flows (for different baskets); allow one enabled revision per `(WhatsApp account, Meta Flow ID)`, never one Flow total per account. Each opening must match the exact account, Flow ID and Flow JSON version to its verified binding.
15. Each screen maps to one final `basket_mold_positions.id`, shows every eligible alternative with its image and value, then quantity `0,1,2,3,4,5,6`, followed by explicit **Próximo**. Quantity `0` means remove that position; still submit a valid offered product ID for the position. Keep the required image on each alternative as a release gate: the current v5 only shows the selected product image, and Meta's official components page returned HTTP 429 during this review, so validate the exact image-bearing option component/version in Meta's Flow Validator and both WhatsApp numbers before publish.
16. Basket quote rule is taken from the canonical mold order writer: each selected product uses `offer_price` only when `is_offer=true` and that value is non-null/non-negative; otherwise use `price`. Add `basket_molds.hidden_adjustment` once. Also add `conditional_hidden_adjustment` only when its rule is enabled and its configured product is selected with quantity greater than zero. Store these hidden adjustments only in the server-side intent/snapshot; never include their individual values in Flow data or the customer summary. Reprice against current canonical data before asking for confirmation and again in the confirmation transaction.
17. Flow ends with payment choice, then customer/address resolution: run the canonical Brazilian phone-variant resolver for the sender E.164 and link only one active customer; show and confirm their address, or collect the missing customer/address fields. Keep opaque Meta sender IDs separate and send ambiguous/inactive/no-phone identities to human review. Persist the submitted identity/address as intent data; create/update the canonical customer as part of the explicit order-confirmation transaction so an unconfirmed Flow does not create a partial customer record.
18. The precise order of screens is: one screen per sorted mold position; payment method; then customer and delivery address. For a unique active customer, use `resolve_customer_by_phone_v1` (which delegates to the canonical Brazil phone-variant resolver). Present one active default address for confirmation; if none exists, show the sole active address when there is one, offer a choice when there are several, or collect a new address when there are none. Multiple defaults are inconsistent data and require explicit address choice, not silent selection. If no active customer is found, collect the customer name and full address. If the resolver returns ambiguity or only an inactive match, do not guess; mark the intent for human review. The canonical address model is `customer_addresses` (`street`, `number`, `complement`, `neighborhood`, `city`, `state`, `postal_code`, `reference`, `block`, `google_maps_url`, active/default flags). Treat the chosen address as an order delivery snapshot; only save a new customer/address after explicit order confirmation.
19. Every native Catalog checkout remains its own intent, including when it follows a Flow in the same conversation. The webhook cart has item IDs and quantities but does not carry the delivery/payment decisions collected by the basket Flow. The Admin conversation panel must therefore show a safe item list and a clearly labeled current-price estimate from the verified local mapping; never present Meta's reported item price as the order price. Do not create the canonical `orders` row until customer, delivery address, payment method, current price, and customer confirmation have been resolved. A future explicit review/confirmation step may create one separate order and invoice for this Catalog intent.

## Intake and confirmation state machine

```text
Meta webhook
  -> signature verified
  -> durable event dedupe by account + Meta message ID
  -> normalize event and resolve account by phone_number_id
  -> create independent intent
  -> validate identity, Flow version or Catalog mapping, current price and stock
  -> enqueue summary with one-time confirmation action
  -> customer confirms
  -> revalidate price/stock + validate sender/account/conversation/token
  -> one transaction: canonical order + items + stock reservation + intent conversion
```

- Intent states: `received`, `needs_review`, `awaiting_confirmation`, `reprice_required`, `declined`, and `converted`. Acceptance and canonical order creation are one transaction, so there is no persisted `confirmed`-but-not-converted state. Failures keep the event and intent visible for retry/review; they do not silently create orders.
- The confirmation token is random, stored as a hash, and bound to the intent, account, conversation and sender identity. The webhook reply also has to match the reply/button ID and expected customer context.
- Flow completes after payment and customer/address collection. The final product list and grand total are sent as a WhatsApp message after the Flow submission, not as another editable basket screen. The summary contains product names and quantities, one server-calculated total, and an explicit confirmation button; it omits item prices and hidden adjustments. Payment and delivery address stay in the private/order snapshots and have already been handled in the Flow.
- Treat the Flow token as a capability: use it only in memory to resolve the hash already stored for a Flow session, never log or persist the raw token. Use `replyToMessageId` to correlate a reply to the outbound Flow message when required. The Flow `response_json` may contain name/address data; a versioned adapter must whitelist normalized fields before storing an order snapshot.
- Repeated Meta delivery, worker retry, repeated confirmation, and concurrent confirmation must all return the same intent/order result. Use unique constraints plus row locking in the writer transaction; do not use “check then insert” without a lock/constraint.
- An accepted intent creates exactly one `public.orders` row and its `public.order_items`. The event-to-order binding, stock reservation, outbox work and state transition must commit or roll back together.
- The order starts in the backend's verified entry state that appears as “Produção” in the current Admin workflow. Do not invent a new status. Dispatch/Bling actions remain behind their existing gates.

## Schema proposal for the next database migration

### `whatsapp_ordering_private.whatsapp_order_intents_v1`

Store intent ID, linked webhook event ID, WhatsApp account, Meta WABA ID and phone-number ID, source kind (`flow`/`catalog`), Meta message ID, conversation/customer when unambiguous, opaque provider sender ID, nullable phone, Flow ID/schema version or catalog ID, state, quote revision, a normalized `intake_snapshot`, server-priced `quote_snapshot`, total, currency, hashed confirmation token, final order ID and timestamps. Do not add `expires_at` to represent a business timeout. Preserve only fields required to explain/reprice/confirm the order; raw webhook PII remains in the existing access-controlled event record.

Unique key: one intent per webhook event; any business key also includes WhatsApp account. References to canonical orders are unique so one intent cannot convert twice.

### `whatsapp_ordering_private.meta_catalog_product_links_v1`

Map `whatsapp_account_id + catalog_id + product_retailer_id` uniquely to an active canonical `products.id`. Include sync/verification metadata and timestamps; never infer a link from SKU/name or use the webhook price as a mapping. Missing or ambiguous mapping routes the intent to review and does not create an order.

### Database API and privileges

- Keep ledger/mapping tables in the unexposed `whatsapp_ordering_private` schema with no `anon`/`authenticated` grants; enable RLS as defense in depth and grant schema/table access only to `service_role`.
- Because PostgREST does not currently expose the custom schema, Edge Functions call narrow `public` `SECURITY INVOKER` RPC entrypoints with empty/fixed `search_path` and fully qualified table names. Revoke function execution from `PUBLIC`, `anon`, and `authenticated`; grant only to `service_role`. Keep service credentials server-only. Do not add the private schema to the global PostgREST exposure list for this feature.
- The confirmation transaction must lock the intent, validate its current revision and token hash, recalculate all product prices/stock, create an idempotent order with `source='manual_whatsapp'` and a stable `whatsapp-intent:<uuid>` key, call the verified reservation contract, then mark the intent converted.
- Insert a notification/outbox row only after the intended canonical event exists and only through the already verified outbox contract. Confirm that the order INSERT does not trigger the Loja “pedido recebido” message for `manual_whatsapp`.

## Compilação PostgreSQL das funções críticas (27/10/2026)

- O parser pglast 8.7 aceitou as instruções externas das três migrations e 28 dos 29 corpos PL/pgSQL. A única rejeição é escrita de campo em `%ROWTYPE` na função `prepare_confirmation`; ela também ocorre num exemplo mínimo, e não ocorre quando o PostgreSQL compila a função real.
- A criação das funções `whatsapp_order_intent_ingest_v1`, `whatsapp_order_intent_prepare_confirmation_v1` e `whatsapp_order_intent_confirm_v1` passou em PostgreSQL 17.6 descartável, com tabelas de linha sintéticas e sem dados. Os stubs não representam o baseline Supabase completo: referências SQL, tipos compatíveis em runtime, triggers, ACL, RLS e efeitos de negócio continuam pendentes de staging isolado.

### Ruling de isolamento do endpoint Flow candidato (27/10/2026)

O inventário canônico mostrou `whatsapp-flow-data-exchange-v1` ativo na versão 76 como proxy legado. O nome do diretório local greenfield colidia com esse endpoint. A candidata agora usa `whatsapp-flow-data-exchange-greenfield-v1`, com import map/entrypoint próprios em `supabase/config.toml`. Antes de validar, o Flow Manager da Meta deverá apontar cada WABA ao URI novo; a rota antiga não será substituída.
